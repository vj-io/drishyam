# Security model

Drishyam takes untrusted photos from anyone on the internet and drives an agent
with them. This page lists what an attacker controls, what they could try, and
the control that stops it. Every control named here has a test in `tests/` (the AWS WAF rules and the page headers policy in the CDK synth tests, `tests/test_infra.py`), except the pre-push secret scan, which is process.

## What an attacker controls

- The bytes of an uploaded image, its declared `Content-Type` and `Content-Length`.
- The query string (`pixel_cap`, `usd_cap`, `seconds_cap`, `chaos`, `pace_ms`).
- The `X-Drishyam-Replay` header (decisions to resume a killed job).
- The review request body (`token`, `finding_id` or `not_assessed`, `decision`, `reviewer`, `note`).
- Anything painted on the photographed structure (graffiti, signs, text).
- For the MCP server: the arguments an LLM passes to each tool, including the free-text `why` and `reason`
  that end up in the trace.

## Threats and controls

| Threat | Control | Where | Test |
| --- | --- | --- | --- |
| Decompression bomb (tiny file, huge canvas or deep pixels) | Width, height, bit depth and channels are read from the PNG IHDR / JPEG SOF header; refused above 25 MP or 100 MB of decoded pixels **before** any pixel is decoded; decoded size must match the header | `imaging.sniff_size`, `decode_image` | `test_imaging.py::test_rejects_non_images_and_bombs`, `::test_decoded_bytes_budget` |
| Oversized body / slow memory exhaustion | Body is read in chunks and abandoned the moment it passes 4.4 MB; lying `Content-Length` is refused; the Lambda Function URL also caps the request payload at 6 MB, in which a binary body travels base64-encoded | `web._read_capped` | `test_web.py::test_rejects_bad_uploads` |
| Non-image or polyglot upload | Content-Type allow-list (JPEG, PNG) **and** magic-byte sniffing; OpenCV decodes only after both pass | `web.create_job`, `imaging.sniff_size` | `test_web.py::test_rejects_bad_uploads` |
| Budget abuse (huge jobs) | Every cap range-checked server-side (pixels 2–100 %, $0.0001–0.05, 1–30 s; `pace_ms` 0–1500 with at most 25 s of waiting per job); job halts inside one step of any cap; Lambda timeout 60 s, no reserved concurrency (this account's Lambda quota is 10, which is the cap); AWS WAF rate limits per IP, answered with 429 and a JSON error: 10 job starts per 120 s, 30 kill and review calls per 60 s, 300 requests per 60 s; CloudFront serves IPv4 only, so a client cannot rotate through an IPv6 /64 to get past them | `web.create_job`, `governor.check`, `infra/drishyam_stack.py` | `test_web.py::test_rejects_bad_params`, `::test_pace_ms_pauses_between_looks_but_not_the_job_clock`, `test_agent.py::test_pixel_cap_is_never_exceeded`, `test_infra.py::test_waf_rate_limits_per_ip` |
| Forged replay decisions | Replay is decoded from base64url JSON (16 KB max), then every entry is checked: action in the allow-list, integer coordinates inside the image, level 0–3, at most 200 | `web._parse_replay`, `agent.validate_replay` | `test_agent.py::test_replay_input_is_validated`, `test_web.py::test_replay_header_validation`, `::test_a_deeply_nested_replay_header_is_a_422_not_a_server_error` |
| Agent approving its own critical finding, or marking an area it did not assess as checked | The state machine only lets `actor="human"` leave `pending_review` or resolve a `not_assessed` entry (checked by eye: nothing found or defect found); only `/api/review` and `drishyam review` call either transition, so there is no agent code path, MCP tool or planner strategy that approves, rejects, closes, downgrades or resolves; new evidence can raise criticality, never lower it; an MCP redraft keeps a person's resolution and cannot write one | `findings.decide`, `resolve_entry`, `Finding.agent_update`, `mcp_server.draft_work_order` | `test_findings.py::test_agent_cannot_decide_or_downgrade`, `::test_only_a_person_resolves_a_not_assessed_entry`, `::test_only_the_human_surfaces_call_the_human_transitions`, `test_agent.py::test_critical_finding_blocks_work_order_and_agent_cannot_close_it`, `test_mcp.py::test_tool_list_is_the_allow_list`, `::test_a_check_by_eye_survives_a_redraft` |
| Tampered or replayed work order | Work orders are HMAC-SHA256 signed with a secret of at least 32 characters; on AWS it is a 64-character Secrets Manager secret generated by CloudFormation, read by ARN once per cold start and never logged; constant-time comparison of the MAC as written, so a token has one spelling (a re-padded MAC, or one with `+` `/` for `-` `_`, is refused) and every decision forked from it names the same `prev_token_sha256`; 7-day expiry; a decided finding cannot be decided again, nor a resolved entry resolved again; an index the order does not list is refused | `findings.sign`, `verify`, `apply_review`, `apply_resolution`, `web._signing_key` | `test_findings.py::test_tampering_expiry_and_reviewer_validation`, `::test_a_signed_token_has_one_spelling`, `::test_resolution_refusals`, `test_web.py::test_review_flow_and_tampering`, `::test_checked_by_eye_over_http`, `::test_signing_key_from_secrets_manager` |
| Prompt injection via text in the image | There is no OCR. The optional LLM planner receives a numeric digest only (it never sees pixels). The MCP server does return crops and the heatmap as images, so a vision-capable MCP client can see text painted on a structure: that client must treat image content as untrusted, and in any case it can only call the 12 allow-listed tools, none of which approves, resolves a not-assessed entry, writes files or runs commands. For the planner: (numbers, generated ids, fixed class and model names); its reply must be one allow-listed strategy with range-checked parameters or it is discarded; 2 s timeout; rule planner always decides on failure | `planner.validate`, `Job.digest` | `test_planner_governor.py::test_planner_sees_numbers_and_fixed_names_only`, `::test_validator_rejects`, `::test_20_timeouts_and_20_malformed_all_recover` |
| Planner endpoint used for SSRF | Planner URL comes only from server env; must be `https://` or plain `http://` to an exact loopback host (`127.0.0.1`, `::1`, `localhost`; look-alikes such as `localhost.evil.com` are refused) | `planner.HttpPlanner` | `test_planner_governor.py::test_http_planner_url_policy`, `::test_http_planner_rejects_lookalike_loopback_hosts` |
| Shell or file access from the agent | The agent has no shell tool and no file-write tool; MCP tools are a fixed allow-list; `open_image` resolves real paths under an allow-listed root only | `mcp_server.py` | `test_mcp.py` |
| Text an MCP client writes into the trace (`why`, `reason`) | At most 200 characters, whitespace folded, printable only, else refused; stored as data in the record's `rationale` and never read back as an instruction by any code path | `mcp_server._call`, `request_human_review` | `test_mcp.py::test_why_is_optional_bounded_and_printable`, `::test_every_tool_on_a_bridge_photo` |
| XSS in the UI | Strict CSP (`script-src 'self'`, no inline script or style, no `eval`); DOM built with `textContent`; base64 images checked against a strict alphabet before use | `infra/headers.json`, `public/js/*` | `tests/e2e` runs under the production CSP and fails on any violation |

## Known limits (stated, not hidden)

- The web demo keeps no work orders: a signed work order lives in the browser,
  and the downloaded `work_order.json` is its copy. Each accepted review also
  prints one log line (on AWS an EMF record in CloudWatch Logs, kept 14 days):
  the work order and finding ids, the decision, and SHA-256 hashes of the
  reviewer name and of the token before and after, never the name or a token
  (a hash of a guessable name is a pseudonym, not a secret). There is no
  approval database: the PRD's DynamoDB + SNS approval store was not built.
  (`test_web.py::test_one_emf_line_per_review_on_lambda_with_hashes_only`)
- One pre-review token can be signed into conflicting decisions; each carries
  `prev_token_sha256` (a hash of the token it came from, never its MAC), and the
  CloudWatch review log orders them. The same holds for resolutions (checked by eye). The reviewer name is
  self-asserted, for a resolution as for approve: "checked by eye" records who said they looked, not proof that
  anyone did. Its optional note (200 printable characters at most) is stored in the signed order as data and never
  logged. (`test_findings.py::test_two_decisions_forked_from_one_token_are_visible_siblings`,
  `::test_a_person_resolves_each_not_assessed_entry`)
- `/api/review` and `/api/kill` share one WAF rate rule (30 per IP per 60 s);
  both are cheap and size-capped, and a review is HMAC-gated.
- KILL in the browser goes through `/api/kill`, which sets a shared flag (the
  DynamoDB table `DRISHYAM_KILL_TABLE` names on AWS; in a local run, a dict in
  the one uvicorn process) that the running job reads after every step; the
  governor then halts before the next look. The flag is needed because a Lambda
  Function URL does not pass the browser's disconnect through to the function,
  so an aborted stream alone does not stop a job. The job id and its kill token arrive in the job's first
  record, so a KILL pressed before that record is held by the page and sent the moment it arrives; the server
  reads it after the next step record, so the first look still runs
  (`tests/e2e/test_ui_mock.py::test_kill_before_the_first_record`). When the server does not confirm a KILL
  within 6 s, or sends no first record within 15 s of a KILL pressed before it, the page stops showing the job
  (or cancels the upload) and says the server may still be running it, up to its time cap; it calls neither a
  kill (`test_kill_the_server_never_confirms`).
  The operator-wide switch is `DRISHYAM_KILL_SWITCH=1` (env) or the `DRISHYAM_KILL_FILE` flag file.
- Anyone holding a token can review it: there is no multi-tenant auth (a PRD
  non-goal).
- Within the kill-and-review WAF limit a caller can write junk KILL flags (each a small DynamoDB
  item with an `exp` TTL attribute, which DynamoDB deletes lazily, usually within
  a few days) but cannot stop another viewer's job without that job's 144-bit
  kill token, which is hashed into the flag's key.
- `pace_ms` lets a caller keep a function instance busy longer per job (at
  most 25 s of waiting); the job-start rate limit bounds how many such jobs one
  address can start.
- The `chaos` drills are reachable by anyone on purpose (they are the failure
  demo for judges); each is bounded by the same caps as any job.
- The deployed function (AWS Lambda) refuses to start without a signing key
  (`DRISHYAM_SIGNING_KEY_SECRET_ARN`, or `DRISHYAM_SIGNING_KEY`), so tokens never
  silently become per-instance.
- Uploads are refused when their header implies more than 100 MB of decoded
  pixels (bit depth and channels count, not only width × height).
- The privacy detectors run on a copy whose long side is 640 px (`privacy.DETECT_SIDE`), so on a 4608-px photo a
  face is seen at about 1/7 of its size. How small a face YuNet still finds at that scale was not measured (the
  repository has no face images), so a small face in a large photo can reach a full-resolution look unblurred.
